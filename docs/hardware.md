## 1. Профиль железа и выбор модели

- CPU: Intel Core i5-13400F (10 ядер / 16 потоков)
- RAM: 32 GB
- GPU: NVIDIA GeForce RTX 4060 Ti (присутствует в системе)
- Профиль по таблице курса: `TODO` — сверьте характеристики выше с таблицей профилей курса и впишите свой класс железа

**Наблюдение:** `uv sync` по умолчанию ставит CPU-only сборку `torch` с PyPI
(так у `pyproject.toml` остаётся портируемым для машин без GPU — в том числе,
вероятно, для машины проверяющего). Из-за этого `device: "auto"` изначально
разрешался в `"cpu"`, хотя в системе есть RTX 4060 Ti. Локально (не меняя
`pyproject.toml`/`uv.lock`) поставлена GPU-сборка
(`uv pip install "torch==2.14.0+cu130" --index-url
https://download.pytorch.org/whl/cu130`, версия CUDA подобрана под
установленный драйвер) — после этого `device_map="auto"` сам подхватил
GPU. Оба замера — до и после — приведены ниже.

## 2. Результаты замера (`make bench`)

| Метрика | CPU (`torch` из PyPI, по умолчанию) | GPU (локальная CUDA-сборка `torch`) |
|---|---|---|
| Устройство | cpu | cuda:0 |
| dtype | bfloat16 | bfloat16 |
| Время загрузки модели, сек | 2.09 | 2.88 |
| tokens/sec (медиана по 3 прогонам) | 7.48 (8.01 / 7.48 / 7.42) | 35.84 (35.89 / 35.84 / 35.71) |
| Пиковая RSS, MB | 1500.7 | 2192.5 |

GPU даёт ~4.8× ускорение генерации ценой более долгой загрузки (перенос
весов на устройство) и большего RSS процесса (CUDA-контекст держится в
оперативной памяти хоста помимо VRAM). Оба прогона сделаны одним и тем же
`uv run python -m src.bench`, менялась только установленная сборка `torch`.

## 3. Разбор найденных дефектов

### Дефект 1 — имя модели захардкожено в обход `params.yaml`

**В чём был:** имя `"Qwen/Qwen3-0.6B"` было прописано строкой сразу в трёх
местах — `src/model.py` (`load_model`), `src/generate.py` (строка с печатью
имени модели) и `src/bench.py` (поле `model` в отчёте).

**Как проявлялся:** изменение `model.name` в `params.yaml` ни на что не
влияло — код продолжал грузить исходную модель, потому что `params` в этих
местах вообще не читался. Это прямое нарушение главного правила курса: имя
модели должно жить ровно в одном месте.

**Как исправлен:** все три места переведены на чтение
`params["model"]["name"]` из уже загруженного конфига вместо строкового
литерала. Проверено проверкой `tests/check.sh` (пункт 2), которая
подменяет модель на `HuggingFaceTB/SmolLM2-135M-Instruct` и убеждается, что
загрузилась именно она — по `model.config.name_or_path`.

### Дефект 2 — зависимости в `pyproject.toml` без версий

**В чём был:** `dependencies` в `pyproject.toml` перечисляли пакеты
(`torch`, `transformers`, `accelerate`, `numpy`, `pyyaml`) без каких-либо
версионных ограничений.

**Как проявлялся:** `uv sync` мог подтянуть любые последние версии на
момент установки — у разных участников курса получались бы разные версии
`transformers`/`torch` с разным поведением (например, разной поддержкой
`enable_thinking` у Qwen3), а поломка сборки в CI через несколько недель
стала бы вопросом времени, а не «если».

**Как исправлен:** зависимости зафиксированы диапазонами версий
(`torch>=2.4,<3`, `transformers>=4.51,<5` — минимальная версия с поддержкой
Qwen3, `accelerate>=0.34,<1`, `numpy>=1.26,<2`, `pyyaml>=6.0,<7`), точный
слепок фиксируется `uv.lock` после `uv sync`.

### Дефект 3 — `bench.py` мешает время загрузки модели с генерацией

**В чём был:** таймер `t0` стартовал до `load_model`, но в цикле замера
`elapsed = time.perf_counter() - t0` каждый раз считался от того же самого
`t0` — то есть в каждую итерацию накапливались и загрузка модели, и все
предыдущие прогоны генерации. Отдельного прогрева не было, а `load_time`
был жёстко прописан как `0.0` вместо реального замера.

**Как проявлялся:** `tokens_per_sec` получался неправдоподобно маленьким и
почти не зависел от длины сгенерированного ответа — цифра была разбавлена
временем загрузки модели (которое на порядок больше времени одной
генерации) и линейно росла с номером итерации.

**Как исправлен:** время загрузки теперь меряется отдельным таймером
(`t0` → `load_time` сразу после `load_model`, до цикла генерации). Перед
замером выполняется `warmup_runs` прогревочных прогонов, результат которых
не попадает в статистику. В цикле замера таймер `t` стартует заново на
каждой итерации, так что `elapsed` — это время ровно одной генерации.
`tokens_per_sec` считается как медиана по `measure_runs` прогонам.

### Дефект 4 — генерация не воспроизводится

**В чём был:** в `params.yaml` был включён сэмплинг (`temperature: 0.7`),
а функция `set_seed()` в `src/model.py` была определена, но нигде не
вызывалась — ни в `generate.py`, ни в `bench.py`.

**Как проявлялся:** два последовательных запуска `make generate` давали
разный текст ответа, хотя задание явно требует детерминированности при
`temperature = 0` (`tests/check.sh`, пункт 3, сравнивает `diff` двух
прогонов).

**Как исправлен:** `temperature` в `params.yaml` установлена в `0.0` —
это включает жадный поиск (`do_sample=False` в `src/model.py`), который
детерминирован сам по себе. Дополнительно `set_seed(params["generate"]["seed"])`
теперь вызывается в начале `main()` в `generate.py` и `bench.py` — чтобы
воспроизводимость не зависела от того, останется ли где-то ещё сэмплинг.

## 4. Дополнительное исправление (не входит в 4 заявленных дефекта)

`src/bench.py` использовал модуль `resource`, которого нет на Windows —
скрипт падал бы с `ModuleNotFoundError` на нативном Windows-окружении.
Замер пиковой RSS переведён на `psutil` с веткой для Windows
(`peak_wset`) и веткой для Linux/macOS (прежний `resource.ru_maxrss`,
поведение не изменилось).
